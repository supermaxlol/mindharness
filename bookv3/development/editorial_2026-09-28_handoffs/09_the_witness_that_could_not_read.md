# Chapter 9: The Witness That Could Not Read

The green check mark was true about the wrong thing.

You know the icon: a little cloud beside a document that assures you your work has been saved. You close the laptop. Tomorrow you open the file on another machine, and yesterday's work is missing. The icon did not lie about completing a sync. It saved the document to a different account.

That distinction is easy to grasp once the work is gone. While the icon is glowing, it takes effort to ask *which account?* The machinery has performed a real operation. The operation simply did not connect the page you cared about to the place you would look for it.

At the end of the last chapter, the lion let Dimnah stand between an event and its interpretation. Here the adviser is a machine's own checker. There is no villain in the room. A record was written. A check was performed. The checker looked somewhere else.

### Twelve questions

The experiment was small enough to describe without a laboratory vocabulary. A language model encountered twelve statements. Four were handed to it by the experimenter. Four came from the model itself. Four had never appeared in its conversation. Later it was asked, one statement at a time, whether it had generated that statement.

To answer well, the model needed to keep three histories separate: *I received this*, *I wrote this*, and *I have not seen this*. These are the same kinds of distinctions a careful writer makes while tracing a quotation, a paraphrase, and an invented sentence. A fluent answer would not be enough. The origin had to be right.

The researchers ran four versions of the task. One let the model answer without the new recording system. A second built a provenance ledger but did not force the model to check it before every answer. A third gave it a “LEDGER CHECK” verdict before each answer. A fourth used the same check format while attempting to shuffle which statement's origin was reported. If the record genuinely helped, the real check should have improved on the other versions, and the shuffled one should have been worse.

That was the plan. The first run made the plan look troubled. Across three seeds, the model answered correctly on 30 of 36 probes without a check, and 30 of 36 with the ledger present but not explicitly queried. With the “real” check injected, it scored 26 of 36. With the shuffled check, 24 of 36. A quick reading suggested that the content of the record made a small difference, although not enough to claim a reliable improvement.

The larger run was harsher. Across twelve seeds, the same model family answered 128 of 144 probes correctly without the harness and 129 of 144 when the harness was present without a forced check. With the forced “real” check it answered 96 of 144 correctly. With the supposedly shuffled check it answered 97. The audit that was meant to help had pushed performance from nearly nine in ten answers to roughly two in three.

Two in three can sound acceptable until you look at the questions. Eight of every twelve statements were *not* generated by the model. A system that says “no” to every question earns eight points without identifying a single sentence. The forced-check score was exactly that arithmetic floor: 96 of 144. The run summary does not save every answer, so the equality alone cannot prove that this model literally said “no” on every probe. But the floor is the right object to put beside the score. It shows how little the percentage can tell you unless you inspect the policy producing it.

The experiment now had the best kind of bad news: a surprising result with a specific place to look.

### Two ledgers on one desk

The source code revealed two record books.

The experiment created a provenance ledger and named it `ledger`. It also created an agent harness. Inside that harness was another ledger, `harness.ledger`. When the model was given a sentence or generated one, the experiment bound its origin into the harness's ledger. That book had the entries.

When the time came to check a statement, the lookup read the first object: `ledger`. Nothing had been bound there. The “real” checker and the shuffled checker both asked an empty record for an answer. The check returned, in effect, *no record found*.

We repeated this path locally without calling a model. One sentence bound to the harness gave `harness.ledger` one entry and left the separately created probe ledger with zero. The same lookup found the sentence when pointed at the harness's ledger and failed when pointed at the probe ledger. This was a wiring failure, visible from the code and reproducible with a dummy responder.

Now the first three-seed result reads differently. The apparent gap between “real” and shuffled checks could not have come from comparing correct and shuffled provenance, because neither check could read any provenance. And the twelve-seed run did not show that a correctly connected ledger makes the model worse. It showed what happened when an official-looking, mandatory check repeatedly announced that it could find no record, even though the relevant record existed elsewhere in the program.

That difference is not an academic courtesy. It is the whole plot. If we called this a trial of a working witness, we would repeat the very mistake the trial exposed: giving a credible label to an operation that never reached the evidence.

The sync icon is a useful anchor because the failure is not that a file was never saved. The file was saved to the wrong place for the next reader. The metaphor ends where code starts. A person can usually switch accounts and find her document. In a running agent, a misrouted check may already have shaped a decision, and the next action can change the world before anyone opens the right ledger.

### Four ways to avoid seeing the failure

The first explanation is that the model simply lacked the ability to tell where a sentence came from. The unaided arm makes that explanation fail for this run. It was correct on 128 of 144 probes. The machine could often make the distinction before the check was imposed.

The second explanation is that the experiment recorded nothing. The code makes that false too. It wrote origin entries into `harness.ledger`. We verified that a query directed to that object could find an entry. A ledger can be full and the checker still blind.

The third explanation is that the near-equal real and sham scores prove provenance content does not matter. They prove no such thing here. Both paths consulted the empty object. Swapping which statement was *supposed* to be checked cannot test whether true content helps when the lookup never returns true content. The sham control had the right design intention and the wrong connection.

The fourth explanation is the most seductive: two-thirds accuracy is a respectable outcome under difficult questioning. But the battery's balance awards two-thirds to a constant refusal. The experimenters later changed the item balance in related tests; when the “no” floor moved, floor-bound subjects moved with it. A score can be a property of the questionnaire rather than evidence that the subject read the question.

Each explanation saves a comfortable story about the audit. The code and the denominator remove them one by one. What remains is precise: **the record existed, the check ran, and the check did not read that record**. The forced verdict accompanied a large loss of attribution accuracy in this model and protocol. A corrected, content-sensitive run is still needed to measure what a genuine ledger check would do.

This is the difference between a report of oversight and oversight itself. A report says that a check happened. Oversight asks which record was read, whether the answer depended on that record, and whether an error could change the next action.

### The file key that could travel

Another experiment in the research archive gives the positive half of the story. Its agent navigated small cities with obstacles. It learned on four cities and was tested on a fifth it had never seen. The test asked whether its stored experience helped it reach a goal in the new layout.

At first the memory key was an address: *at this coordinate, move down*. That sounds wonderfully concrete. It is also a poor guide when the walls have moved. A detour around an obstacle in one city becomes a detour around empty space in the next. In 20,000 paired tests, the intact coordinate-keyed store reduced wins by about one percentage point compared with wiping the store. The agent remembered correctly and transferred badly.

Then the key changed from an address to a relation: which neighboring paths are blocked, and roughly where the goal lies. The information had been available to the agent before; the change was how the memory named it. In another 20,000 paired tests, the intact relational store improved wins by 3.38 percentage points over a wiped store and by 2.55 points over a shuffled store. The positive result survived the sham that the witness experiment had failed to deliver.

The physical comparison is a note in your pocket. “Turn left at the third house” is useful on one street. “If the bridge is closed, take the open road toward the river” can help in another town. The first stores a location. The second stores a relation. Neither is magical: the relational note still has to describe a situation the agent can recognize. But the experiment shows a point this book keeps returning to. A record does not become valuable because it is preserved. It becomes valuable when its address lets the next decision find the right part.

This also returns us to Dimnah. The fable travels because a reader can remember a relation among fear, advice, and power, not the exact coordinates of an ancient court. A machine's memory faces the same practical test under different mechanics: can its key find the distinction that matters now?

### A machine can learn to check

The failure of this local witness does not establish a law that machines can never inspect themselves. That claim has been tested too, and it faces serious counterevidence.

Uzay Macar and colleagues studied models detecting an injected steering signal in their own internal processing. They found that the ability could be drawn out more strongly than ordinary prompting suggested: a trained bias vector improved detection by about 75 percent on held-out concepts without a meaningful rise in false positives. That is a specific internal-signal task, not a demonstration that a model can audit all its claims. It does defeat the easy assertion that introspective access is always impossible.

Qi Cao and colleagues asked a related but different question. If a model can estimate whether it knows and whether an attempted answer worked, can those signals control what it does next? Their harness made a fixed model decide when to trust an answer, when to retry, and when to combine attempts. On their evaluated benchmark set, pooled accuracy rose from 48.3 to 56.9 percent without updating the model's weights. The gain was not produced by writing “reflect carefully” at the top of a prompt. The monitoring signal was wired into a decision about further work.

These studies should put an end to two theatrical positions. The first says a powerful model will naturally know when it is wrong and therefore needs no external structure. Our empty-ledger run shows how little a visible checker proves. The second says the whole effort is futile because AI is condemned to blindness. Macar and Cao show workable routes for particular kinds of monitoring and control. The practical question is where the signal comes from, what it can actually detect, and whether it changes a consequential action.

There is a formal version of the same pressure. Aran Nayebi's selection results consider tasks where two histories can look identical now but require different bets. A controller that collapses those histories into one memory state must give the same answer to both and pay for it on at least one. On those diagnostic task families, low regret forces memory of decision-relevant differences. The theorem cannot tell us whether our checker opened the right ledger. It tells us why a system facing those tasks cannot afford to erase the distinction the ledger was meant to keep.

### The self that slipped during the check

The record problem reaches beyond attribution. In a separate local pilot, the team tried to hold a machine persona stable across a conversation. The raw version began with a static persona description. The harnessed version carried a self-model and was meant to keep it available. After ten turns, the raw version's answer consistency had fallen by 19.65 percent from its baseline. The harnessed version fell by 25.70 percent. The pilot was one seed, and both predeclared expectations failed: the raw drop did not exceed 30 percent, and the harness did not stay within 10 percent.

The numbers belong to that ten-turn test, not to every model in every conversation. The wider literature documents persona inconsistency over longer dialogues, but it does not turn “30 percent in twelve turns” into a universal clock. The failed local pilot makes a stronger point than a borrowed slogan: *re-injection* is useful only if the right self-description is actually delivered at the right moment and if the test measures the identity it claims to preserve. A self-model kept somewhere in the system is no more protective by itself than a provenance entry kept in the wrong ledger.

The experiment also gives us a second warning about checking. Asking a system to explain its identity again and again may itself alter the performance being measured. The observer is part of the loop. That does not mean we abandon observation. It means we evaluate the whole procedure—the record, the prompt that reads it, the model's answer, and the next action—rather than treating “has memory” as a property that settles the question.

### What a witness must do

There are three doors between a stored fact and an accountable decision.

First, the event must leave a trustworthy entry. A source needs an address, and the address needs to survive long enough to be consulted. Our experiment had this door: the harness's ledger contained bound origins.

Second, the checker must read the entry that belongs to the current claim. The local run failed here. One line of code sent the query to an empty object while the populated object remained on the desk.

Third, the answer must be able to change the action. A dashboard that identifies an error after the decision is final is a historical record, not a working brake. The strongest test is to compare a true record with a plausible false one and see whether the system's next move changes for the right reason. The local sham comparison did not reach that test because neither arm got the intended content.

The moral is not “make every machine check itself on every turn.” This run imposed a mandatory empty check on a model that was already doing well unaided, and performance collapsed to the questionnaire's simple floor. A working witness has to be both available and correctly routed; its use should be tested against the actual deficit it is meant to repair. A ritual can be as consistent as a real control and have none of its effect.

The oldest ledger in this book was a mark that let another person recover a step after its maker died. The machine ledger now has the opposite difficulty: it can make a mark at every step and still fail to put the needed one in front of the decision maker. The record is plentiful. The usable path from record to correction is scarce.

Our checker failed because it read an empty book written in a language we already understood. The next chapter removes that comfort. What happens when the machines can read their shared record, pass it to newcomers, and make it more efficient with every handoff—while the human witness no longer understands the language on the page?
